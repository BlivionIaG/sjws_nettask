  guard ≥ 80 MiB/s and p99 ≤ 1.5 ms; hard zeros incl. retries and `refused_per_ip`; heap 2g. A window is
  valid only if generator CPU ≤ 80 % of its cores. Thresholds are not lowered.
- #417 / PR #459 (merged `067ac18`) already made the producer POST lean (raw keep-alive socket). It did not
  publish a 1k-stream window that was unsaturated.
- #465's harness work (local copy in `/workspace/bench-416/harness`, not on master) shows the closed-loop
  generator is self-loaded at **any** stream count: 2–4 streams still reach 106–145 % of 2 cores, because
  every stream POSTs as fast as its round trip allows. Generator CPU follows chunk rate, not stream count.
- So the problem is per-chunk generator cost, and a closed loop that always pushes until something saturates.

The budget that decides it: 100 MiB/s of 1 KiB chunks is ~102 400 chunks/s, each one sync POST + response
parse + one frame read on the consumer side, all on the generator. Mode (A) allows 160 % of 2 cores, about
**15.6 µs of generator CPU per chunk**, including loopback TCP work the kernel charges to the generator.
Mode (B) allows 240 % of 3 cores, about 23.4 µs.

## #415: what changes (drafted on this branch)

1. **Lean consumer** (`StreamLoad --lean-consumer`, default on for binary; `LEAN_CONSUMER=0` turns it off).
   The `:stream` POST and the `replies` GET go over one raw keep-alive socket per consumer. The chunked body is
   de-chunked in place (`ChunkedIn`), frames are read into one reused buffer, and stamps are parsed from bytes.
   This removes `HttpClient` (selector thread hand-off, per-read `ByteBuffer` lists, `ofInputStream` queue)
   and the per-frame `byte[]` + `String` + `Long.parseLong` from the hottest generator path. `:stream` uses
   `postOnce` (no resend, so a reconnect can't open a second session).
2. **Leaner producer.** The data-frame request head is built once per stream (path, token and length are
   fixed) instead of string-concatenated per POST. Responses are parsed from bytes (status digits,
   case-insensitive header match in place) instead of `String.split` / `toLowerCase` per header line.
3. **Pacing** (`--rate-mib-s R` / `RATE_MIB_S`, unset = today's closed loop). Each stream sends one chunk
   every `streams × 1024 / (R × 2^20)` s (≈ 8.9 ms per stream at R = 110), random phase. Late slots are caught
   up, not dropped (wrk2-style). Each chunk carries its actual send stamp at data[0..20) and its **scheduled
   send time** at data[20..40). **Paced windows report `p99_us` from the scheduled send time**
   (`latency_basis: "scheduled"`, ruling Q1), so a stalled producer or a server that falls behind can't hide
   backlog. Closed loop keeps the send stamp (identical there). `p99_send_us` and `p99_sched_us`
   (`chunk_latency_send` / `chunk_latency_sched` with histograms) are always reported side by side, with
   `offered_mib_s`, `sched_late_pct` and `sched_lag_max_us`. Paced runs need `chunk_bytes ≥ 40`. **No
   validity rule changes:** a producer behind schedule because the server is slow is a server result, not an
   invalid window.
3b. **Gate rule (ruling Q1, disclosed on PR 8, Architecture sign-off pending).** `gate.sh` runs abs and A/A
   windows paced at `GATE_RATE_MIB_S` (default 110). `agg.py` passes only paced windows (offered ≥ 100,
   basis `scheduled`) on median achieved ≥ 100 MiB/s and p99 < 1 ms, guards unchanged (≥ 80 MiB/s,
   p99 ≤ 1.5 ms). After each `abs-NN`, a closed-loop info leg `cl-NN` runs; it's printed beside the window and
   never counted (`CLOSED_LOOP_INFO=0` skips it). One `floor` leg at `FLOOR_RATE_MIB_S` (default 10) gives
   the generator's latency floor, printed beside every window and never subtracted (ruling Q5). Each window
   line shows offered, achieved, scheduled and send p99, closed loop, and floor.
4. **Histogram export.** `chunk_latency.hist` (sparse LatBag buckets) plus `hist_sub_bits`, so (B)'s
   multi-process windows can be merged exactly rather than by averaging p99s.
5. `gate.sh` defaults `LOADGEN=java` (one.sh's default is the CPython `drive.py`, which can't drive 1k).
   `one.sh` gains `RATE_MIB_S`, `LEAN_CONSUMER`, `SERVER_JAVA_OPTS`, `GEN_JAVA_OPTS` pass-throughs, all empty by
   default so a gate window is unchanged unless set.

Not drafted yet (only if (A) still self-loads after 1–3; ruling Q3: (B) first, selector-based only if
(B) can't hold the rate):
- **(B) 3/5 split** (pre-approved, disclosed): `GEN_PROCS=n` in `one.sh` starts n StreamLoad processes on CPUs
  0-2, each with `streams/n` streams and disjoint group ranges, and sums their CPU. A small `merge-gen.py`
  merges result.json files: sum bytes/requests/retries, merge `hist` buckets, recompute p50/p90/p99 with the

- An NIO selector generator (one event loop per core instead of 2 000 virtual threads). This is the bigger
  rewrite. Only do it if JFR on the generator (`GEN_JFR=1`) shows VT park/unpark or the poller dominating.

### How #415 is benchmarked (bench rules, nothing local while another slot holds the locks)

Everything runs as `flock /tmp/sjws-bench.lock` for the whole run, starts at load1 < 3, uses the foreign-CPU
sampler (NOISY = foreign > 0.5 core avg, foreign java/mvn/load seen, or any load1 ≥ 6), and writes
`DONE #415-<step> <ISO> <PR comment URL>` to `/workspace/bench-queue.md` even when invalid. Queue order is
inceptor's. Jars are built beforehand with `flock /tmp/sjws-mvn.lock nice -n 19 mvn -B -q -DskipTests package`,
or taken from CI.

0. **Smoke** (2 min): source launch of StreamLoad at 32 streams, binary, lean consumer on and off.
   Check `errors == 0`, `chunk_samples > 0`, paced: `p99_sched_us ≥ p99_send_us` and `latency_basis == "scheduled"`, a correct LAST end, and `open_sessions_after_drain == 0`.
1. **Generator calibration** (pick (A) or (B); the server jar is master for every leg):
   - Cost per chunk: closed loop at 1k/64 with `LEAN_CONSUMER=0` vs `=1`, 3 windows each. Report
     `client_cpu_pct_of_wall / (mib_s × 1024)` = generator µs per chunk.
   - Offered-rate ladder with lean on: `RATE_MIB_S` = 25, 50, 80, 110 at 1k/64. Find the highest rate where
     `client_cpu_pct ≤ 160` with `p99_sched_us` ≈ `p99_send_us` and low `sched_late_pct` (generator keeping schedule). Run `GEN_JFR=1` once at the
     highest rate to see where generator CPU goes.
   - Low-rate floor: `RATE_MIB_S=10` gives the generator-induced latency floor (VT scheduling on 2 carriers).
     If that floor is already near 1 ms p99, the generator can't measure the gate and (B) or NIO is needed
     whatever its CPU.
   - Decision: if 110 MiB/s fits in 160 % → mode (A). Else draft (B) and repeat the ladder at 240 %. Else
     report to inceptor with the per-chunk cost table before any NIO rewrite.
2. **Gate**: `gate.sh master.jar master.jar` (absolute §13 windows are on the current server, 5–8 valid),
   paced at `GATE_RATE_MIB_S=110` with the `cl-NN` closed-loop info legs, the `floor` leg and the mandatory A/A.
   It's judged only after Architecture signs off on the rule change. For the generator change itself
   (harness-only), an ABBA of old vs new generator against the same server jar, ≥ 9 valid blocks per arm plus
   A/A (G1: |t| < 2, delta ≤ larger sd), shows the new generator doesn't shift the measured server latency at a
   rate both can drive (e.g. 25 MiB/s).
